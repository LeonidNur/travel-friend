# Рабочий процесс команды

## Роли

- Frontend / Product: отвечает за Mini App, Telegram, UX и интеграцию экранов.
- Backend / AI: отвечает за Supabase, API, AI, RAG и серверную логику.
- UX/UI: отвечает за UX, дизайн-систему, компоненты и интерфейсы.
- Технический советник (ChatGPT): архитектура, декомпозиция задач, продуктовая логика, технические решения и ревью процесса разработки.
- Codex: реализация небольших законченных задач и работа строго по ТЗ.
- Разработчик / техлид: принимает решения, управляет git и проверяет результат.
- Маркетинг / исследование продукта: рынок, конкуренты, пользователи.

## Базовая схема веток

```text
main
↓
develop
↓
task branch
↓
PR в develop
↓
review и одобрение → merge в develop
↓
отдельное release decision для promotion в main
```

## Правила работы

- Одна задача = одна ветка.
- Одна ветка = одна законченная задача.
- Нельзя смешивать в одной ветке несвязанные изменения.
- Если задача вырастает, её лучше разделить, а не тащить в один PR.

## Подключение нового разработчика

1. Прочитать `README`.
2. Прочитать Engineering Handbook.
3. Изучить Roadmap.
4. Получить небольшую задачу.
5. Создать отдельную task branch.
6. Выполнить задачу.
7. Проверить актуальность документации по правилу ниже.
8. Передать diff на review; обычные feature/docs PR направляются в `develop` и вливаются после проверки и одобрения.

## Проверка документации после задачи

После задачи кратко проверь, какие документы действительно требуют актуализации по [правилам документации](engineering-handbook/documentation-rules.md), и обнови только их. Не нужно массово обновлять README, roadmap, CHANGELOG и dev-log после каждого дня или задачи; отсутствие нерелевантных изменений не мешает завершению работы.
