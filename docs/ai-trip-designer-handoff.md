# Travel Friend — Designer Handoff: Copilot, Trip editor, Draft, Proposal, PDF

**Дата:** 2026-11-07
**Статус:** утверждённая продуктовая логика; дизайн-макеты и конкретная композиция UI ещё не утверждены.
**Приоритет:** этот handoff + [каноническая спецификация](ai-trip-product-spec.md) заменяют конфликтующие положения старого `docs/designer-update.md` в AI/Trip/Proposal части. Ранее принятые решения по Discover, Profile, navigation и Group Chats не менять без отдельной задачи.

## 1. Что проектируем и почему

Пользователи договариваются о путешествии в групповом или личном чате и постепенно собирают программу уровня профессионального туроператора: маршрут, ночёвки, перемещения, занятия по дням, свободные дни и заметки. AI — **помощник внутри Chat/Trip**, не отдельная вкладка и не авторитет над пользователями. Confirmed Trip меняется **только** после единогласного голосования. При необходимости люди делают всё вручную без AI.

Единый mental model: **Chat = обсуждаем → AI Draft = примеряем → Proposal = голосуем → Trip = согласованное → PDF = итоговый документ**. Не превращать 5 сущностей в 5 обязательных экранов: пользователь должен понимать, где он сейчас и на что влияет действие.

## 2. Основная навигация и страницы

**Сохраняем существующую нижнюю навигацию:** Chats / Discover / Trips / Profile. Новый AI tab не нужен.

1. **Chat Room:** сообщения пользователей, кнопка Copilot и явный `@Copilot`; сообщение ИИ с ответом и карточкой Draft; карточки Proposal с голосами и переходом к деталям. Ссылка «Открыть Trip».
2. **Trip overview:** согласованная программа и её степень детализации; секции «Маршрут и даты», «Бюджет», «Транспорт», «Проживание», «Программа и заметки». Различать пустые поля, подтверждённые данные и требующие пересмотра области; понятные CTA «Рабочий черновик», «Предложить изменение», «Готовность программы».
3. **Дни Trip:** список дат и содержимого (события, свободное время, заметки); каждому дню необязательно иметь события и часы. Не навязывать таймлайн с обязательным временем.
4. **Общий рабочий Draft:** одна общая редактируемая версия + сохранённые альтернативы; явные состояния «Черновик / ещё не согласовано». Любой участник может изменить с отображением автора и версии. Отдельная кнопка для «Добавить AI-вариант в черновик».
5. **Proposal details:** один неизменяемый вариант изменения; diff «было → станет» с охватом одного дня / события / отеля / бюджета / комплексного пакета, статус голосования, список участников и собственное решение.
6. **Готовность и PDF:** коллективное «Программа готова» для текущей версии, затем «Сформировать PDF» и «Открыть/Поделиться». Только один сохранённый актуальный PDF; если данные поменялись, показать «PDF устарел».

## 3. Минимальные ключевые сценарии

### А. Copilot по просьбе пользователя

Пользователь нажимает кнопку или пишет `@Copilot`, backend принимает AIRequest. Чат остаётся доступным: лёгкая **голубая подсветка всей области Chat** и статус «Copilot работает…». Другие участники видят состояние и могут писать. **Остановить** может только инициатор. При `completed/failed/cancelled` фон нормализуется. Ответ Copilot — одно общее сообщение со структурированными карточками; no token streaming в первой реализации.

В ответе: объяснение/сравнение, возможные варианты, дата/источник проверенной информации (если API использован), ограничения («Цена не проверена»), кнопка **«Добавить в черновик»** и/или **«Предложить голосование»**. Ни одна кнопка не означает автоматического принятия пользователями.

### Б. Большая AI-программа на 12 дней

Copilot создаёт общий понятный preview: маршрут, дни (включая пустые), проживание/транспорт, ориентировочные расходы/примечания. Пользователь может открыть полный Draft, вручную поменять мероприятия без AI, сохранить альтернативный вариант и выбрать части для голосования. Не показывать сразу десятки голосований по дням. Один связанный пакет можно вынести как **один** Proposal «всё или ничего», независимые части — отдельными.

### В. Ручная правка Trip без AI

Участник открывает Trip, нажимает «Предложить изменение», попадает в редактор/черновик; меняет событие, весь день, отель или бюджет. Сохранение Draft не меняет Confirmed Trip. Затем «На голосование» — создаётся immutable Proposal и карточка автоматически видна в Chat и Trip. Если область уже занята другим pending Proposal — показать понятное предупреждение и не создавать голосование; предложить перейти к активному решению или дождаться закрытия.

### Г. Голосование

В одном блоке: название/суть изменения, разница old→new, цена/известный impact, количество голосов, автор. Участник **сначала выбирает** «Принять» или «Отклонить», **затем отдельно** нажимает «Проголосовать». После отправки решение нельзя менять. Ошибка сети не стирает выбранную опцию. Инициатор не считается проголосовавшим при создании. `reject` любого завершает вопрос, единогласное `accept` обновляет Trip.

Зависимый Proposal: виден в чате/Trip, но кнопки заблокированы с пояснением «Ожидаем решения по …». Если prerequisite отвергнут/устарел — «Требуется пересмотр», а не исчезновение. Blocked dependent не занимает активный lock до попытки разблокировки, тогда сервер заново проверяет совместимость. При одновременном отправлении изменений одной области backend сохраняет первое успешно зарегистрированное, второму пользователю показывает 409 с переходом на существующее голосование. Не обещать умную проверку пересечений экскурсий по часам — это будущее.

### Д. Изменение отеля дороже бюджета

Явно различать: **согласованный бюджет** (не менялся), **оценка стоимости** (возможно превышение) и **проверенная цена** (источник+время). Не блокировать голосование. Если известен конкретный эффект — показать «Оценка превышает бюджет на …», если только возможен — «Стоимость может измениться». Ничего не переписывать скрыто; дать опцию отдельного связанного Proposal об изменении бюджета. Не вставлять пугающие предупреждения для изменений без влияния.

### Е. Готовность и PDF

Любой участник предлагает «Программа готова» для **текущей версии Trip**; все подтверждают. Незаполненные необязательные поля допустимы. После согласия появляется «Сформировать PDF». Он создаётся из подтверждённых данных, без AI и без редактирования содержимого. Если согласована новая правка, статус готовности/PDF становится «Неактуально — появились изменения», перед новой генерацией требуется новое согласие всех. Нет истории PDF-версий в приложении; одна актуальная ссылка. Ранее скачанные копии остаются у пользователей физически.

## 4. Экранная матрица состояний

| Объект | Состояния, которые надо нарисовать | Особенности |
|---|---|---|
| Chat + Copilot | idle, queued, processing, completed, failed, cancelled, timeout | Голубой фон только при активном запросе; переписка доступна; stop только initiator |
| AI message | answer-only, alternatives, full draft preview, partial result, unverified data | Карточки не равны принятым решениям; source/checked time для проверенных offer |
| Working Draft | empty, edited, saved alternative, saving, version conflict, stale base | Видно авторство; конфликт сохранения без silent overwrite |
| Trip overview | empty, partially planned, confirmed content, pending changes, ready for PDF, PDF stale | Readiness != trip completed |
| Day detail | blank day, free-form note, timed events, event without time | No fake mandatory fields; удобно читать длинные программы |
| Proposal | pending, waiting for my vote, my vote submitted, accepted, rejected, cancelled, expired, stale, blocked/dependent | Позволять открыть из Chat и Trip, ясно отображать автора и голоса |
| Vote control | not selected, choice selected, submitting, submitted, error | **Двухшаговое действие**; повторный голос запрещён |
| Proposal overlap | concurrent area busy, locked broader change, stale revision | «Сейчас обсуждается изменение этой части» + ссылка |
| Notifications | bot not started, enabled, muted per type, delivery not available | Доставка не гарантирована, не блокировать решение |
| PDF | absent, ready-to-generate, generating, current, outdated, failed | Приватный доступ, одна сохранённая версия |
| AI tiers | standard/free, premium allowed, premium locked for caller | Ответы premium видны всей группе, право вызова только у premium участника |

## 5. Предлагаемые UX тексты (можно редакционно улучшать)

- «Copilot работает над ответом» / «Остановить» / «Попробовать ещё раз».
- «Это предложение Copilot, оно ещё не согласовано участниками».
- «Добавить в общий черновик» / «Вынести на голосование» / «Обсудить в чате».
- «Согласованная программа» / «Рабочий черновик» / «Требуется голосование».
- «Этот день уже меняют в другом голосовании. Откройте предложение или дождитесь решения».
- «Выбрано: принять. Чтобы отправить голос, нажмите „Проголосовать“».
- «Стоимость может превысить согласованный бюджет. Бюджет автоматически не изменится».
- «Программа согласована, можно сформировать итоговый PDF».
- «PDF устарел: после его создания программа изменилась».
- «Для личных уведомлений сначала откройте диалог с ботом».

## 6. Telegram-уведомления — точки входа

Через Telegram Bot API, не через LLM: новое голосование, напоминания спустя 24 и 72 часа, завершённый результат, отменённые/устаревшие предложения; AI completion опционален. Deep link ведёт на соответствующие Chat/Trip/Proposal. Дизайнеру нужны settings переключатели типов уведомлений и fallback UX «бот не может доставить уведомления». Без ежедневного спама и без требования обязательно включать уведомления.

## 7. Визуальные принципы

Показывать **контент поездки, а не технические карточки БД**. Небольшие, спокойные status labels, ясный приоритет: подтверждённое — основная программа, черновик — маркирован как рабочий, Proposal — отдельный контур решения. Голубая подсветка AI — временная, лёгкая, не перекрывает сообщения. Избегать сложных досок задач, вечных тревожных баннеров, искусственно заполненных дней и «AI-волшебства» без согласия группы. Для mobile Telegram WebView учитывать компактный экран, клавиатуру и длинные программы.

Финальный PDF может визуально напоминать аккуратный туроператорский itinerary: день за днём, логистика, свободные окна, важные заметки. Но PDF не обязан повторять мобильные карточки один в один; это отдельный детерминированный шаблон, который верстается из уже согласованной Trip.

## 8. Что НЕ проектировать сейчас

- Отдельную AI-вкладку и автоматические фоновые AI-сессии.
- Ранговое многовариантное голосование вместо одного proposal accept/reject.
- Прямое бронирование/оплату через Travel Friend.
- Архив всех PDF-версий.
- Редактор безголосовательного подтверждённого Trip.
- AI-powered автоматическое разрешение всех временных и логистических конфликтов.
- Подвижный состав участников group chat; текущие группы фиксированы.
- Экран управления RAG и model routing для обычных пользователей.

## 9. Что передать команде

**Минимальная поставка дизайна:** user flow Chat→Copilot→Draft→Proposal→Trip→PDF; список экранов и состояния выше; clickable Chat/Trip/Draft/Proposal prototype; правила отображения разных уровней достоверности цены; пустые/ошибочные/заблокированные случаи; отдельный PDF visual example. Дизайн передаётся с явной связью к [product spec](ai-trip-product-spec.md), без копирования устаревшего четырёхблочного UX.
