# Pre-Beta Designer Update — UX-01…UX-10

Краткая дельта к предыдущему дизайнерскому handoff. Используйте вместе с [User Flows](user-flows.md), [MVP Scope](mvp-scope.md) и [Design Principles](design-principles.md). Этот документ описывает целевой UX и состояния интерфейса; он не меняет backend contracts.

> Для AI/Trip/Proposal части этот документ дополнен и заменён [дизайнерским handoff от 07.11.2026](ai-trip-designer-handoff.md) и [канонической продуктовой спецификацией](ai-trip-product-spec.md). Решения UX-01…UX-10 вне этой части сохраняются.

## Изменения и уточнения сценариев

### UX-01 — Discover → Public Profile

- Из карточки Discover можно открыть расширенный публичный профиль кандидата и вернуться к той же карточке.
- На карточке и в расширенном профиле доступны одинаковые два финальных действия: **Подходит** (`interested`) и **Не подходит** (`rejected`). Выбор один раз фиксирует решение для кандидата; возврат из профиля не создаёт второе решение.
- При взаимном интересе показать feedback о мэтче и дать перейти в чаты либо продолжить Discover. Не переводить пользователя автоматически.
- Профиль должен показывать текущие данные кандидата: имя, возраст при наличии, город при наличии, bio, Travel Intent и доступные travel preferences.

### UX-02 — Chat → Public Profile

- Из direct Chat открыть профиль собеседника; из Group Chat — профиль любого другого участника.
- Профиль доступен только в контексте участника этого чата. Возврат ведёт в исходный чат.
- Это ознакомительный профиль: действия Discover `interested` / `rejected` не показываются в уже созданном чате.

### UX-03 — Active Travel Intent

- Показывать текущий Travel Intent отдельно от постоянных данных Profile: направление и необязательные даты.
- Редактирование обновляет единственный активный план поездки. При ошибке сохранения введённые значения остаются доступными для исправления/повторной отправки.
- Не предлагать удалить активный план как обычное действие: завершённый onboarding требует наличия активного Travel Intent.

### UX-04 — Onboarding

- Первый запуск проходит обязательные два шага: Profile, затем Travel Intent. Discover становится доступен после завершения настройки.
- В каждом шаге нужны состояния загрузки, ошибки, валидации и успешного сохранения; со второго шага можно вернуться к первому.
- Preview Mode не предусмотрен в первой бете. Каждый пользователь проходит onboarding до Discover.

### UX-05 — Chats List / Chat Room

- Chats List показывает direct/group чаты; для группы — количество и список имён участников. Пустой список ведёт в Discover.
- Chat Room показывает участников, историю, отправку текстового сообщения, пустую историю и переход к поездке.
- Для состояний загрузки и ошибки предусмотреть понятный текст и повторную попытку. Ошибку отправки показывать рядом с composer, сохраняя текст.
- Нужны отдельные состояния списка и комнаты для отсутствия чатов/сообщений, недоступного чата, общей ошибки и временно отсутствующей сети.
- В каждой строке Chats List показывать последнее сообщение, время сообщения и индикатор непрочитанного.
- Расширенные функции мессенджера не входят в этот handoff.

### UX-06 — Group Chat

- Создатель выбирает минимум двух собеседников из существующих direct чатов; вместе с ним группа содержит минимум трёх участников.
- При создании пользователь может задать название длиной до 80 символов; поле необязательное. Пустое название отображается как «Групповой чат».
- Название видно в списке чатов и комнате. Любой активный участник группы может переименовать её из комнаты; при очистке поля используется «Групповой чат».
- Базовые действия: создать группу, переименовать её, открыть, читать/отправлять сообщения, открыть профили участников, перейти к поездке.
- Состав группы фиксирован. Приглашения, добавление/удаление участников, выход и роли администраторов не входят в первую бету.

### UX-07 — Chat → Create/Open Trip

- Из direct или group Chat можно создать Trip. Если для этого чата уже есть незавершённая Trip, открыть её вместо создания дубликата.
- В списке Trip предусмотреть loading, error с повтором, empty и populated; empty state объясняет, как Trip появляется из чата.
- Trip Detail показывает статус, подтверждённые/пока пустые данные, маршрут если он есть, даты если они есть, участников и ссылку обратно в Chat.

### UX-08 — Trip: данные, участники и lifecycle

- Trip — отдельное представление подтверждённого состояния планирования, связанное с исходным Chat.
- При создании все текущие активные участники исходного Chat сразу отображаются как участники Trip.
- Trip creator отображается как атрибуция, не как административная роль.
- Изменение подтверждённого состояния Trip проходит через Proposal и согласование участников; не показывать creator-only редактирование.
- Приглашения, выход, отмена или завершение Trip не входят в согласованный UX первой беты, пока их lifecycle не утверждён отдельно.

### UX-09 — Proposal и согласование

Базовый AI Copilot и Proposal flow входят в обязательный scope до первого внешнего теста. Это утверждённый целевой UX, а не описание уже реализованного поведения:

1. Copilot встроен в Chat/Trip flow. Он помогает сформулировать вариант и может подготовить Proposal; отдельная AI-вкладка не вводится.
2. Proposal показывает предлагаемые изменения и решение каждого участника: принять или отклонить.
3. Любое отклонение завершает Proposal как rejected; accepted требует единогласия. Только backend после успешного решения атомарно обновляет Trip.
4. Если исходный Trip/block уже изменился, показать stale state и объяснить, что Trip не изменился; устаревший Proposal нельзя принять.
5. До принятия Proposal Trip показывает предыдущее подтверждённое состояние. AI не меняет Trip напрямую и может завершиться без Proposal.

### UX-10 — Язык, валидация и единообразие

- Для текущего русскоязычного интерфейса использовать согласованные русские названия действий, экранов и статусов.
- Ошибки показывать рядом с полем и/или действием, называть следующий шаг пользователя и сохранять исправляемый ввод.
- Одинаковые состояния загрузки, пустого результата, ошибки и повтора должны выглядеть и называться согласованно в Discover, Chats, Profile, onboarding и Trips.
- Для дат использовать человекочитаемое представление, сохраняя единый формат между карточками и деталями.

|---|---|---|
| Telegram bootstrap | loading, auth error | Продолжить в приложение после серверной проверки Telegram; при ошибке объяснить повторный вход |
| Onboarding: Profile | loading, validation error, save error, saved | Исправить данные или перейти к Travel Intent |
| Onboarding: Travel Intent | loading, validation error, save error, saved, complete error | Вернуться к Profile либо завершить onboarding |
| Discover card | loading, load error, candidate, no candidates, decision error, match feedback | Открыть профиль; принять одно решение; после match перейти в Chats или закрыть feedback |
| Discover Public Profile | loading, not found/error, loaded | Вернуться к той же карточке; доступны те же два решения, что в Discover |
| Chat List | loading, error, empty, populated, message preview, unread | Показать последнее сообщение/время/unread; открыть direct/group чат; создать группу из доступных direct companions |
| Chat Room | loading, error, not found, empty history, populated history, send error, offline | Повторить загрузку; сохранить текст при send error; открыть профиль участника; показывать «Создать поездку» или «Открыть поездку» |
| Group Chat create/rename | no eligible companions, optional title entry (80 chars max), choose participants, validation/create/rename error, saving, saved | Название при создании необязательно; blank показывает «Групповой чат». Любой активный участник может переименовать; сохранять draft при recoverable error |
| Chat participant profile | loading, unavailable, error/retry, loaded | Возврат в тот же Chat; без Discover actions |
| Trips List | loading, error/retry, empty, populated | Открыть Trip; из empty state перейти к созданию Trip из Chat |
| Trip Detail | loading, not found, error/retry, forming/empty blocks, populated, pending proposals | Показать confirmed state, автора-создателя как атрибуцию и возврат в Chat; подтверждённые изменения принимать только через Proposal |
| AI Copilot | idle, request in progress, response, no Proposal, error, cancelled | Открывается из Chat/Trip; может подготовить предложение, не меняет Trip самостоятельно |

## Что изменилось относительно прежнего handoff

- Уточнён единый Discover decision flow между карточкой и расширенным профилем.
- Добавлены backend-backed профили участников Chat, включая группы.
- Active Travel Intent отделён от Profile и редактируется как один активный план.
- Подтверждено отсутствие Preview Mode и обязательный onboarding.
- Chats List получает последнее сообщение, время и unread indicator; доставка данных относится к будущему Live Chats block.
- Group Chat получает название при создании и rename flow; состав остаётся фиксированным.
- AI Copilot и базовый Proposal flow включены в обязательный pre-beta UX; AI не меняет Trip напрямую.
- Подтверждено, что creator Trip — атрибуция; изменения confirmed Trip идут через Proposal.
- В Chat предусмотрено явное Create/Open Trip действие; `409` остаётся техническим fallback.
- Добавлены состояния ошибок/повтора, offline, пустых списков и устаревшего Proposal.
- Уточнены ограничения первой беты для Group Chat: фиксированный состав, пользовательское название и rename без invitations/leave/remove/admin roles.

Implementation gaps и нерешённые продуктовые вопросы приведены в [Internal UX Alignment Report](internal-ux-alignment-report.md), а не являются дополнительными требованиями этого handoff.
