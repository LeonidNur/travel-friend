# Правила документации

Вся проектная документация по умолчанию ведётся на русском языке. Это касается как крупных документов, так и небольших рабочих заметок. Английский язык допустим только там, где он неизбежен: в названиях технологий, библиотек, команд и кода.

`README.md` остаётся главным документом проекта. Его можно аккуратно дополнять и уточнять, но нельзя радикально сокращать или переписывать с нуля без явного разрешения. Для нового участника команды README должен оставаться надёжной точкой входа, а не краткой заглушкой.

Документация должна честно отражать только то, что уже реализовано. Если функция ещё не готова, о ней нельзя писать как о завершённой. Если что-то находится в планах, это должно быть видно именно как план, а не как факт поставки.

## Назначение документов

- `README.md` — обзор проекта и входная точка для читателя.
- `docs/roadmap.md` — текущие приоритеты и этапы.
- `docs/technical-hardening-backlog.md` — технические риски и gates.
- `CHANGELOG.md` — значимые изменения проекта.
- `docs/dev-log.md` — значимые инженерные решения, эксперименты и результаты проверок.
- Domain-specific документы — соответствующие контракты, архитектурные решения и процедуры.

## Актуализация и Definition of Done

Документация остаётся частью Definition of Done. Для каждой задачи проверь, какие документы действительно требуют актуализации с учётом изменённого поведения, контракта, архитектурного решения или важной операционной процедуры, и обнови их. Не требуется обновлять все перечисленные документы после каждой задачи или по ежедневному ритуалу. Отсутствие изменений в одном или нескольких документах само по себе не делает задачу незавершённой, если содержание этих документов остаётся актуальным.

Значимые инженерные решения, эксперименты и результаты проверок фиксируй в `docs/dev-log.md`, когда они важны для дальнейшей работы; не превращай его в обязательный ежедневный отчёт.

Когда появляется новый документ или меняется существующий, важно смотреть на него не изолированно, а в связке с остальными материалами. Документация проекта должна быть согласованной: если одно место говорит одно, а другое — противоположное, это уже ошибка, которую нужно исправить.
