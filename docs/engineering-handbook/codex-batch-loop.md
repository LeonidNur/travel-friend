# Controlled batch-loop workflow

Этот workflow применяется только к явно одобренному пользователем batch из 5–10 небольших hardening-задач. Он организует очередь и проверку; общий порядок работы, выбор skills, границы скоупа и формат отчёта остаются в [task protocol](codex-task-protocol.md), [Codex rules](codex-rules.md) и [skills workflow](codex-skills-workflow.md).

## Подготовка batch

До начала реализации Codex фиксирует одобренные задачи в исходном порядке. У каждой задачи должны быть краткие цель, scope, ожидаемый результат и применимые проверки. Неясную задачу нельзя уточнять догадками или заменять самостоятельно выбранным пунктом backlog.

Один batch может выполняться в одной feature/chore-ветке, если все задачи ведут к одному согласованному результату. Независимые изменения, для которых нужны отдельные PR, оформляются отдельными batch. Для каждого batch сохраняются остальные обычные правила веток и PR из project workflow.

## Состояния задачи

Для каждого пункта используется ровно одно состояние:

- `pending` — задача одобрена и ожидает своей очереди;
- `in_progress` — выполняется только эта задача;
- `passed` — задача завершена, её проверки прошли, результат и риски записаны;
- `blocked` — продолжение остановлено из-за неясного scope, решения, проверки или внешнего условия;
- `skipped` — пользователь явно исключил задачу из текущего batch; причина записана.

Начальное состояние всех пунктов — `pending`. Codex переводит следующий пункт в `in_progress` только после того, как предыдущий получил `passed` или был явно исключён пользователем как `skipped`. Неоднозначность не считается основанием для автоматического пропуска.

## Исполнение и проверка

Для каждой задачи Codex последовательно:

1. Проверяет scope задачи и релевантные текущие источники истины.
2. Применяет `verification-loop` после изменения, выбирая его фазы и проектные проверки по типу и риску задачи. Полный набор фаз не запускается механически, если часть проверок не относится к задаче.
3. Запускает нужные проверки до перехода к следующему пункту. Для изменения верифицируемого поведения проверка должна покрывать именно этот пункт; общая проверка всего batch не заменяет её.
4. Записывает изменённые файлы, проверки с результатами, найденные в scope и вне scope замечания.
5. Ставит `passed` только если изменения соответствуют одобренному результату и все применимые проверки прошли.

Если проверка не проходит, Codex может исправить обнаруженную ошибку в scope текущей задачи и повторно запустить применимые проверки. Если исправление требует выхода за scope или ошибку не удаётся устранить, задача получает `blocked`, причина и диагностика записываются, а batch останавливается. Не переходить к следующему пункту, пока текущий не стал `passed`.

## Условия остановки

Остановить batch и пометить текущую задачу `blocked`, если:

- требуется security-sensitive или продуктовое решение, которого нет в одобренном scope;
- scope, ожидаемый результат или применимый контракт неясен;
- требуется destructive operation или действие с внешней/production-системой;
- после исправлений в scope любая обязательная проверка всё ещё завершается ошибкой или её нельзя выполнить.

Codex фиксирует причину, доказательства и конкретный вопрос или условие для возобновления. До ответа или устранения условия остальные задачи остаются `pending`. Их нельзя молча пропускать.

Находки вне текущего scope заносятся как `TODO` или `risk` с кратким контекстом и не исправляются в этом batch. Batch не выполняет commit, merge, push, deployment или production changes автоматически; ограничения на commit из task protocol продолжают действовать.

## Журнал и итоговый отчёт

В ходе исполнения Codex ведёт компактный журнал по каждому пункту:

```text
[state] Название задачи
Изменения: файлы или «нет»
Проверки: команда/проверка — PASS/FAIL/не выполнена (причина)
Находки: только относящиеся к пункту; отдельной строкой — вне scope
```

Финальный отчёт содержит:

- список пунктов в исходном порядке и итоговые состояния;
- изменения по каждому `passed` пункту;
- проверки и результаты отдельно для каждого пункта;
- `blocked`/`skipped` причины и условия продолжения;
- риски и TODO, включая находки вне scope;
- подтверждение, что автоматические merge, push, deployment и production changes не выполнялись.

Batch завершён только когда каждый пункт имеет состояние `passed` или явно подтверждённое пользователем `skipped`. Если batch остановлен, отчёт отражает текущие состояния и оставляет непроработанные пункты `pending`.
