# Workflow использования Codex skills

Этот документ фиксирует не продуктовую функциональность, а способ работы Codex в Travel Friend. Он нужен, чтобы задачи решались предсказуемо: с понятным набором инструкций, правильным выбором skills, контролем скоупа и одинаковым форматом итогового отчёта.

## Зачем проекту Codex skills

Codex skills помогают не смешивать разные типы работы в одну универсальную инструкцию. В Travel Friend это важно по трём причинам:

- у проекта есть разные зоны ответственности: frontend, Telegram Mini App, backend, Supabase, документация, диагностика, review;
- для каждой зоны нужны разные практики, проверки и уровень осторожности;
- маленькая задача не должна превращаться в архитектурную сессию, а сложная задача не должна решаться по шаблону "один и тот же подход для всего".

Skills позволяют Codex быстрее понять контекст и выбрать подходящий workflow без лишних догадок.

После этого обновления стандартный набор для frontend-задач в проекте считается таким: `frontend-patterns`, `coding-standards`, `verification-loop`, `git-workflow`.

## Чем отличаются AGENTS.md, skills, subagents и разовое ТЗ

- `AGENTS.md` задаёт общие правила проекта: как работать, чего не делать, как оформлять результат.
- skills — это локальные рабочие модули с конкретными практиками и знаниями для отдельных типов задач.
- subagents — это отдельные исполнители для узких проверок, параллельной экспертизы или специализированного анализа.
- разовое ТЗ — это конкретная задача с ограниченным скоупом, которую нужно выполнить здесь и сейчас.

Практически это работает так:

- `AGENTS.md` отвечает на вопрос "как мы вообще работаем в этом репозитории";
- skills отвечают на вопрос "какой рабочий подход применить к этой задаче";
- subagents отвечают на вопрос "нужно ли вынести часть проверки или анализа в отдельную специализированную пару глаз";
- разовое ТЗ отвечает на вопрос "что именно должно измениться в этой задаче".

## Как выбирать skills по типу задачи

### Frontend / UI задачи

Использовать:

- `frontend-patterns`
- `coding-standards`
- `verification-loop`
- `git-workflow`

Подключать при необходимости:

- `e2e-testing` для пользовательских сценариев;
- `nextjs-turbopack`, если задача затрагивает dev/build поведение Next.js.

### Telegram Mini App задачи

Использовать:

- `frontend-patterns`
- `coding-standards`
- `verification-loop`
- `git-workflow`

Подключать при необходимости:

- `e2e-testing` для проверки критичных экранов и сценариев Mini App;
- `security-review`, если задача касается Telegram auth, обработки `initData` или границ доверия;
- `nextjs-turbopack`, если затрагиваются особенности сборки, dev server или производительности Next.js.

### Backend / API задачи

Использовать:

- `backend-patterns`
- `api-design`
- `coding-standards`
- `verification-loop`

Подключать при необходимости:

- `security-review` для аутентификации, авторизации, входных данных и чувствительных операций;
- `tdd-workflow` для новых endpoint-ов, изменений контрактов и багфиксов на серверной стороне.

### Supabase / database задачи

Использовать:

- `backend-patterns`
- `api-design`
- `coding-standards`
- `verification-loop`

Подключать при необходимости:

- `security-review` для RLS, доступа к данным, секретов и границ доверия;
- `tdd-workflow` для миграций, репозиториев и сценариев, которые можно проверить тестами.

### Documentation-only задачи

Использовать:

- `documentation-lookup`
- `git-workflow`
- `verification-loop`

Подключать при необходимости:

- `tdd-workflow` обычно не нужен, если задача действительно затрагивает только документацию и не меняет код.

### Bugfix / diagnostic задачи

Использовать:

- `frontend-patterns` или другой релевантный доменный skill
- `coding-standards`
- `verification-loop`

Подключать при необходимости:

- `e2e-testing`, если проблема проявляется в пользовательском сценарии;
- `nextjs-turbopack`, если баг связан с dev/build поведением Next.js;
- `backend-patterns`, если проблема находится на серверной стороне;
- `documentation-lookup`, если нужна сверка с официальной документацией по библиотеке или фреймворку.

### Review / security задачи

Использовать:

- `security-review`
- `coding-standards`
- `verification-loop`

Подключать при необходимости:

- `api-design`, если review касается контрактов API;
- `backend-patterns`, если затронуты серверные границы;
- `e2e-testing`, если нужно подтвердить поведение на уровне сценариев.

## Правило старта задачи

Перед любыми изменениями Codex должен явно и кратко написать:

- какие инструкции он прочитал;
- какие skills он применяет;
- какие skills он не применяет и почему;
- какие файлы планирует менять;
- какой скоуп задачи он считает допустимым.

Это нужно не для формальности, а для контроля границ. Если выбранные skills не очевидны, Codex должен объяснить выбор словами, а не молча переключаться между workflow.

## Правило завершения задачи

После изменений Codex должен:

- перечислить изменённые файлы;
- кратко объяснить, что добавлено или изменено;
- указать, какие проверки запускались и какие не требовались;
- назвать результат проверок;
- отдельно перечислить риски и TODO, если они остаются.

Для docs-only задач проверки обычно ограничиваются проверкой структуры и здравым смыслом. Если код не менялся, `typecheck`, `build` и другие продуктовые проверки обычно не нужны, и это следует явно указать.

## Когда использовать subagents

Subagents стоит использовать только тогда, когда есть реальная польза:

- параллельная проверка независимых частей;
- отдельная экспертиза по безопасности, архитектуре или качеству;
- необходимость быстро собрать несколько точек зрения на сложную задачу.

Subagents не нужны для каждой маленькой задачи. Если задача простая и укладывается в один рабочий поток, лишнее распараллеливание только добавляет шума.

## Роль внешнего ECC-репозитория

Внешний ECC-репозиторий можно рассматривать как источник идей, примеров workflow и шаблонов организации работы. Но он не является живой зависимостью проекта Travel Friend.

Это означает:

- мы можем брать оттуда подходы и формулировки;
- мы не строим рабочий процесс так, будто репозиторий синхронизируется сам;
- изменения в Travel Friend должны жить в его собственной документации и правилах;
- внешние обновления не меняют проектный workflow автоматически.

## Практическое правило для этой команды

Если задача маленькая, Codex выбирает минимально достаточный набор skills и работает строго по ТЗ.
Если задача затрагивает несколько зон ответственности, Codex сначала уточняет набор инструкций и только потом меняет файлы.
Если задача docs-only, он не выходит за пределы документации.
