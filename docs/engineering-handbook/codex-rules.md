# Правила для Codex

Codex в проекте Travel Friend нужен как исполнитель небольших и чётко очерченных задач. Он не должен принимать продуктовые решения вместо команды, придумывать направление развития продукта или расширять скоуп по собственной инициативе. Его задача — взять понятную задачу и реализовать её аккуратно, предсказуемо и без лишних сюрпризов.

Перед изменениями Codex сначала показывает короткий план. В этом плане должно быть видно, какие файлы он собирается затронуть и в каком порядке будет работать. Только после этого он вносит правки. Такой порядок нужен не ради формальности, а чтобы команда заранее понимала, что именно изменится.

Когда работа завершена, Codex должен кратко объяснить, что было сделано и почему выбран именно такой путь. Если задача затронула проверки, он запускает `typecheck` и `build`, а если что-то не удалось выполнить, честно сообщает причину. В конце он перечисляет открытые TODO или оставшиеся риски, если они действительно есть.

Есть несколько вещей, которые Codex делать не должен.

- Он не делает изменения «заодно», если они не относятся к задаче.
- Он не добавляет зависимости без явного разрешения.
- Он не переписывает `README.md` без отдельного указания.
- Он не меняет код приложения, если задача помечена как `docs-only`.
- Он не расширяет скоуп работы только потому, что рядом заметил ещё один возможный рефакторинг.

Если задача касается только документации, Codex работает только с документами. Код приложения, бизнес-логика и вспомогательные модули при этом остаются нетронутыми. Это важное правило, потому что docs-only задачи должны улучшать знание о проекте, а не менять сам продукт.

Хорошая работа Codex в этом проекте выглядит не как большое количество правок, а как точное попадание в задачу. Чем меньше лишнего движения вокруг, тем выше качество результата.
