# Codex task protocol

Этот документ — единый рабочий цикл Codex для обычных задач. Он задаёт проверку и handoff на human review; [controlled batch loop](codex-batch-loop.md) добавляет только управление одобренной очередью.

## Вход задачи и контекст

Задача задаёт цель, scope, критерии приёмки, ограничения и особые проверки. Если существенный scope или решение нельзя определить из ТЗ и источников, уточни его до зависимых изменений.

Перед работой:

1. Проверь репозиторий, выбранную ветку и `git status`; не затирай существующие изменения.
2. Прочитай `AGENTS.md`, этот protocol и только релевантные правила, skills и источники истины.
3. До правок коротко сообщи выбранные skills/workflows и почему другие не нужны, планируемые файлы и границы задачи.

Не перечитывай несвязанные документы и не принимай список файлов в инструкциях за требование менять их все.

## Обычный verification loop

Для каждой отдельной задачи:

1. Уточни approved scope и критерии приёмки.
2. Изучи минимальный необходимый контекст и проверяемое текущее поведение.
3. Проверь рабочее дерево и ветку; сохраняй существующие изменения пользователя.
4. Внеси минимальные изменения в scope.
5. Запусти применимые проверки из матрицы ниже.
6. Если проверка выявила in-scope ошибку, диагностируй её, исправь и повтори применимые проверки. Не вводи фиксированного числа попыток.
7. Если повторяющаяся ошибка неясна, прогресс остановился или требуется выйти за scope, остановись со статусом `BLOCKED`, диагностикой и условием продолжения. Находку вне scope запиши как риск/TODO; не исправляй её.
8. При успешных проверках покажи diff, результаты и оставшиеся риски для human review.

При изменении существующего пользовательского flow, контракта или поведения проверь затрагиваемые соседние сценарии, в том числе для feature-задач. Выбирай targeted checks пропорционально риску; полный E2E suite нужен только если этого требует изменение.

Проверка подтверждает только покрываемое ею поведение. Общая проверка не заменяет targeted check для конкретного изменённого сценария.

## Выбор проверок

Выбирай проверки по типу, риску и затронутому контракту. Не запускай полный generic build/typecheck/lint/test/security набор без причины.

| Тип изменения | Базовые применимые проверки |
|---|---|
| Docs-only | `git diff --check`; проверь Markdown links/anchors, если менялись ссылки, и соответствие scope |
| Frontend | `cd apps/mini-app && npm run check`; дополнительные targeted tests, typecheck или build — когда они покрывают конкретный риск или не входят в выбранную команду |
| Backend | Релевантные backend tests для изменённого behavior/contract. Для DB integration применяется `cd apps/backend && ./scripts/local-test-db.sh test` с disposable PostgreSQL |
| Bugfix/integration | Проверка исправленного сценария и затронутых соседних сценариев; добавь проверки соответствующих frontend/backend контрактов по необходимости |

Frontend `npm run check` и backend disposable DB test соответствуют командам текущего CI. Если применимая проверка пропущена или недоступна, укажи причину и остаточный риск.

## Завершение и human review

В handoff укажи изменённые файлы, краткий результат, выполненные/пропущенные проверки, risks/TODO и полный либо достаточный для review diff. Codex оставляет изменение для human review и останавливается до commit, push, merge или deploy. Леонид решает, делать ли commit после review. Для Git/PR процесса см. [workflow](workflow.md).

Задача готова к review, когда критерии приёмки выполнены, применимые проверки пройдены либо их пропуск явно объяснён, а diff остаётся внутри согласованного scope.
