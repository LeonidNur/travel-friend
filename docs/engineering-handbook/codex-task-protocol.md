# Универсальный task protocol для Codex

Этот документ задаёт универсальный порядок работы Codex в Travel Friend.

Общие правила не нужно повторять в каждом ТЗ. Они уже задаются проектными инструкциями, а конкретное ТЗ должно только уточнять саму задачу, ограничения и ожидаемый результат.

## Назначение

- этот документ задаёт универсальный порядок работы Codex в Travel Friend;
- общие правила не нужно повторять в каждом ТЗ;
- конкретное ТЗ только уточняет задачу и ограничения.

## Что Codex всегда читает перед задачей

Перед любой задачей Codex должен опираться на:

- `AGENTS.md`;
- `docs/engineering-handbook/codex-rules.md`;
- `docs/engineering-handbook/codex-skills-workflow.md`;
- этот task protocol;
- релевантные файлы самой задачи.

Это базовый слой инструкций. Пользователь не обязан каждый раз повторять его в prompt.

## Что пользователь указывает в коротком ТЗ

Короткое ТЗ должно содержать только переменные части задачи:

- задача;
- ветка;
- тип задачи, если это полезно;
- скоуп;
- что сделать;
- что не делать;
- проверки;
- особые риски или контекст.

## Что Codex обязан написать перед изменениями

Перед правками Codex обязан явно и коротко указать:

- какие инструкции он прочитал;
- какие skills/workflows применяет;
- какие skills/workflows не применяет и почему;
- какие файлы планирует менять;
- где проходят границы задачи;
- какие соседние сценарии может затронуть.

Это нужно для контроля скоупа и для раннего выявления конфликтов.

## Как Codex выполняет задачу

Во время выполнения Codex работает по таким правилам:

- делает изменения маленькими и фокусными;
- не вносит правки "заодно";
- не расширяет скоуп без отдельного разрешения;
- не меняет несвязанные файлы;
- если замечает новую проблему, фиксирует её как `TODO` или `risk`, но не исправляет без разрешения.

## Что Codex обязан сделать после изменений

После завершения работы Codex обязан:

- перечислить изменённые файлы;
- описать, что сделано;
- указать, изменилось ли поведение UI или логики;
- указать, какие проверки запускались и каков результат;
- указать оставшиеся `TODO` и `risk`, если они есть;
- не коммитить изменения самостоятельно.

## Проверки по умолчанию

Если в ТЗ не сказано иное, действуют такие проверки по умолчанию:

- `frontend/code task` — `npm run typecheck` и `npm run build` внутри `apps/mini-app`;
- `docs-only task` — `git diff --check`;
- `bugfix/integration task` — минимальная проверка затронутого сценария плюс `typecheck` и `build`.

Если какая-то проверка не запускалась, Codex обязан честно указать почему.

## Короткий формат будущего ТЗ

Ниже пример короткого ТЗ, которое дополняет этот protocol, а не дублирует его:

```text
Задача: сделать Chat Room MVP.
Ветка: feature/chat-room-mvp.
Скоуп: только apps/mini-app, без backend/Supabase/API.
Что сделать:
- создать /chats/[id];
- показать mock-сообщения;
- добавить disabled/local-only поле ввода;
- добавить AI placeholder внутри чата.
Что не делать:
- не делать реальную отправку сообщений;
- не менять Discover/Profile/Navigation.
Проверки:
- npm run typecheck;
- npm run build.
Финальный отчёт:
- изменённые файлы;
- что сделано;
- проверки;
- риски/TODO.
```
