# Рабочий процесс

Наш рабочий процесс построен так, чтобы идея не превращалась сразу в код. Сначала она проходит человеческое обсуждение с ChatGPT: мы уточняем цель, границы задачи, риски и то, что вообще должно измениться в продукте. После этого появляется архитектурное решение, достаточное для текущего масштаба, но без лишней тяжеловесности.

Текущий checkpoint — persisted backend-backed flow `Profile → Discover → Chats → Trips` и завершённый production rollout 29.10.2026. На дату rollout production migrations/runtime grants и deployment gates прошли, Render backend и Vercel frontend были готовы; это датированное наблюдение, не гарантия последующей непрерывной доступности. Controlled TEAM E2E и authorization checks завершены, но авторизованный Telegram production E2E ещё не проводился. External test требует отдельного preflight/control gate и решения о готовности. См. [roadmap](../roadmap.md) для текущего этапа и [technical hardening backlog](../technical-hardening-backlog.md) для детальных рисков. Самостоятельные slices для Trip lifecycle/write, realtime и safety остаются отдельными work items; AI/RAG отложен.

Следующий шаг — маленькое техническое задание. Оно должно быть достаточно конкретным, чтобы по нему можно было реализовать задачу без догадок, но при этом не превращаться в большой документ ради документа. Затем задача передаётся Codex на реализацию.

Codex работает только в рамках уже понятного скоупа. Сначала он показывает короткий план, потом вносит изменения в файлы, затем объясняет, что именно сделал и почему. После реализации он запускает проверки, которые доступны в проекте и нужны для уверенности в результате, а затем перечисляет оставшиеся риски или TODO, если они есть.

После этого идёт review. Если в коде или документации есть что улучшить, правки вносятся до финализации задачи. Для обычных feature/docs PR базовой и целевой веткой является `develop`, если отдельным release-решением не установлено иное. `main` хранит проверенное состояние, однако конкретный порядок и критерии promotion из `develop` в `main` остаются отдельным release-вопросом и здесь не определяются.

Отдельное правило у нас простое и жёсткое: одна задача = одна ветка = один законченный PR. Если задача распадается на несколько независимых изменений, это уже несколько задач, а не одна большая пачка правок. Так проще ревьюить, проще откатывать и проще не терять смысл изменений.

Критерии готовности для нашей работы не сводятся к «код написан». Задача считается завершённой только тогда, когда понятен результат, выполнены проверки, документация не врёт, а изменения можно спокойно передать другому человеку без устных пояснений.

Обычно это означает, что:

- цель задачи достигнута;
- изменения находятся в одной ветке;
- PR можно ревьюить без догадок;
- проверки пройдены;
- документация обновлена, если это нужно;
- в `main` попадает только завершённая работа.

## Подключение нового разработчика

Когда в команду приходит новый разработчик, он проходит короткий и предсказуемый путь входа:

1. Сначала читает `README`, чтобы понять, что представляет собой проект.
2. Затем читает Engineering Handbook, чтобы увидеть правила работы.
3. После этого изучает `roadmap`, чтобы понять текущий этап и ближайшие шаги.
4. Получает небольшую задачу с ограниченным скоупом.
5. Создаёт feature-ветку под эту задачу.
6. Выполняет работу в рамках согласованного ТЗ.
7. Обновляет документацию, если задача изменила состояние проекта.
8. После проверки feature/docs PR направляется в `develop`, если отдельное release-решение не установило другую целевую ветку.

## Подход к поиску ошибок

Когда что-то ведёт себя не так, мы не начинаем с хаотичных правок. Сначала идёт короткий цикл поиска причины:

```text
Диагностика
→ гипотеза
→ минимальный эксперимент
→ исправление
→ проверка
→ коммит
```

Смысл этого цикла простой:

- диагностика должна отделить симптом от причины;
- гипотеза должна быть конкретной, а не общей;
- минимальный эксперимент нужен, чтобы не перепутать продуктовую ошибку с ошибкой окружения;
- исправление делается только после подтверждения гипотезы;
- проверка должна показать, что поведение действительно изменилось;
- коммит фиксирует не только код, но и найденный вывод.
