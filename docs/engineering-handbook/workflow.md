# Рабочий процесс

Наш рабочий процесс построен так, чтобы идея не превращалась сразу в код. Сначала она проходит человеческое обсуждение с ChatGPT: мы уточняем цель, границы задачи, риски и то, что вообще должно измениться в продукте. После этого появляется архитектурное решение, достаточное для текущего масштаба, но без лишней тяжеловесности.

Следующий шаг — маленькое техническое задание. Оно должно быть достаточно конкретным, чтобы по нему можно было реализовать задачу без догадок, но при этом не превращаться в большой документ ради документа. Затем задача передаётся Codex на реализацию.

Codex работает только в рамках уже понятного скоупа. Сначала он показывает короткий план, потом вносит изменения в файлы, затем объясняет, что именно сделал и почему. После реализации он запускает проверки, которые доступны в проекте и нужны для уверенности в результате, а затем перечисляет оставшиеся риски или TODO, если они есть.

После этого идёт review. Если в коде или документации есть что улучшить, правки вносятся до финализации задачи. Только после этого выполняются финальные проверки, commit, merge в `main` и обновление документации, если изменения затронули рабочее состояние проекта.

Отдельное правило у нас простое и жёсткое: одна задача = одна ветка = один законченный PR. Если задача распадается на несколько независимых изменений, это уже несколько задач, а не одна большая пачка правок. Так проще ревьюить, проще откатывать и проще не терять смысл изменений.

Критерии готовности для нашей работы не сводятся к «код написан». Задача считается завершённой только тогда, когда понятен результат, выполнены проверки, документация не врёт, а изменения можно спокойно передать другому человеку без устных пояснений.

Обычно это означает, что:

- цель задачи достигнута;
- изменения находятся в одной ветке;
- PR можно ревьюить без догадок;
- проверки пройдены;
- документация обновлена, если это нужно;
- в `main` попадает только завершённая работа.
