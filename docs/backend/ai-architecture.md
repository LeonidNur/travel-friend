# AI architecture

> Статус: future design, не реализация. Интеграция AI/Proposal и внешних provider-ов отложена до подключения второго разработчика.

## Роль AI-слоя

AI в Travel Friend — это не автономный исполнитель, а backend-оркеструемый помощник для обсуждений внутри `Chat` и согласования блоков `Trip`. Он работает только через `AIRequest`, создаёт предложения и summary, но не принимает решения за пользователей.

## ChatSummary

`ChatSummary` — это краткая рабочая сводка чата:

- существует на уровне `Chat`;
- обновляется AI-слоем;
- не является пользовательской историей запросов;
- нужна для сжатия контекста и повторного использования в следующих AI-вызовах;
- помогает отделить длинную message history от компактного актуального состояния обсуждения.

`ChatSummary` может отражать:

- подтверждённые договорённости;
- открытые вопросы;
- ограничения участников;
- текущие конфликты и компромиссные варианты.

## AIRequest

`AIRequest` — центральная техническая сущность AI-слоя.

Он описывает:

- кто инициировал запуск;
- кто оплачивает usage;
- в каком контексте выполняется запрос;
- какой результат был получен;
- порождал ли запрос `Proposal` или внешние API-вызовы.

### Типы запуска

`trigger_type`:

- `user`
- `system`
- `scheduled`

### Контекст

`AIRequest` может быть привязан к:

- `Chat`;
- `Trip`;
- обоим контекстам сразу, если запрос касается согласования поездки внутри конкретного обсуждения.

### Что может сделать AIRequest

- обновить `ChatSummary`;
- создать один или несколько `Proposal`;
- инициировать `ExternalAPIRequest`;
- проанализировать изменение состава поездки;
- завершиться без `Proposal`, если подходящего изменения нет.

### Чего AIRequest делать не может

- напрямую менять `Trip`;
- создавать `TripParticipant` или `ChatParticipant`;
- самостоятельно переводить `Proposal` в applied-состояние;
- иметь прямой HTTP-доступ;
- получать секреты приложения.

## Proposal

`Proposal` — это единственный способ, которым AI влияет на подтверждённое состояние поездки.

### Типы Proposal MVP

- `update_destination`
- `update_dates`
- `update_budget`
- `update_transport`

### Происхождение

`origin`:

- `user_ai_request`
- `membership_review`

### Статусы

- `pending`
- `accepted`
- `rejected`
- `cancelled`
- `expired`
- `stale`

### Правила

- При создании proposal сразу создаются `ProposalVote` для всех активных `TripParticipant`.
- Инициатор AI-вызова тоже обязан голосовать.
- Голос можно подать только один раз.
- Любой `reject` завершает proposal.
- `accepted` достигается только единогласием.
- Подтверждённое состояние `Trip` меняется только атомарно в момент `accepted`.

## External API

AI может пользоваться внешними данными только через backend.

Это означает:

- AI не ходит в интернет напрямую;
- backend создаёт `ExternalAPIRequest`;
- provider возвращает `ExternalOffer` как snapshot;
- AI и backend сравнивают варианты через `ProposalExternalOffer`;
- пользователь получает цены, источник, время проверки, условия и безопасную ссылку для самостоятельного перехода.

Travel Friend не покупает и не бронирует за пользователя. Внешние offer-ы лишь помогают согласовать решение.

## Usage

Учёт использования описан через `usage_scope`:

- `user_quota`
- `system`
- `promotional`

Для `user_quota` обязателен `charged_to_user_id`.

Системные AI-процессы не должны расходовать пользовательскую квоту.

### UsageCounter

`UsageCounter` хранит:

- `period_start`
- `period_end`
- `used_count`
- `reserved_count`

Резервирование нужно, чтобы несколько конкурентных AI-запусков не превысили лимит:

проверка квоты
→ резерв
→ запуск `AIRequest`
→ подтверждение расхода или освобождение резерва

## Premium AI

Premium-модель описывается цепочкой:

`Feature → Entitlement → UsageCounter → AIRequest`

Из этого следуют два правила:

- доступ к AI-функциям определяется entitlement-моделью, а не единым булевым полем `is_premium`;
- разные AI-возможности могут иметь разные лимиты, периоды и правила расходования.

Будущая premium-функция `/trip` пока остаётся продуктовой гипотезой и не считается частью MVP.

## Ограничения ответственности AI

AI:

- помогает интерпретировать обсуждение;
- предлагает варианты;
- может сравнивать внешние offer-ы;
- не принимает решения вместо участников;
- не гарантирует точность цен или availability;
- не гарантирует безопасность поездки;
- не заменяет серверную авторизацию, модерацию и security-контроль.

Итоговый принцип простой: AI подготавливает материал для коллективного решения, а доверенное изменение состояния делает только backend после выполнения доменных правил и голосования участников.
