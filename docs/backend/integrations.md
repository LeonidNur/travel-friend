# Интеграции

## Принцип интеграций

Все внешние интеграции Travel Friend проходят через backend. Telegram Mini App не должен иметь прямой доступ к секретам provider-ов и не должен ходить в travel/AI API напрямую.

Текущая архитектура делит интеграции на два слоя:

- обязательные платформенные интеграции;
- внешние provider-интеграции, которые backend и AI Orchestrator используют для enrichment и предложений.

## Telegram

Telegram — обязательная платформенная интеграция MVP.

Backend отвечает за:

- серверную проверку raw `initData`;
- привязку `TelegramIdentity` к `User`;
- доверенную аутентификацию и создание backend-session;
- принятие только тех команд, которые пришли из проверенного пользовательского контекста.

Frontend отвечает только за получение WebApp-контекста и передачу raw данных на backend.

## AI Provider

LLM provider подключается как внешний AI-поставщик.

Он используется для:

- генерации `ChatSummary`;
- анализа предпочтений и ограничений;
- подготовки `Proposal`;
- анализа `TripBlockReview`;
- нормализации и объяснения результатов внешних travel API.

LLM provider не должен:

- напрямую менять `Trip`;
- получать секреты других provider-ов;
- вызываться с клиента.

## Flight APIs

Flight/travel APIs нужны для блока `transport` и связанного budget analysis.

Они используются для:

- поиска вариантов перелётов или других транспортных предложений;
- построения `ExternalOffer`;
- сравнения нескольких provider-ов внутри одного `Proposal`;
- расчёта ценовой вилки на стороне backend.

Flight API не являются системой бронирования Travel Friend. Пользователь получает snapshot и уходит на provider самостоятельно.

## Hotel APIs

Hotel/lodging APIs рассматриваются как provider-категория для ценового и destination enrichment.

Важно:

- в текущей логической модели lodging не является отдельным подтверждённым Trip-блоком;
- hotel-данные могут помогать AI оценивать общий budget, destination attractiveness и компромиссные варианты;
- сами бронирования остаются вне ответственности Travel Friend.

## Maps

Maps/geodata provider-ы нужны как вспомогательный слой:

- place lookup;
- географический контекст направления;
- расстояния и логика перемещений;
- пояснения к транспортным и destination-вариантам.

Maps не являются источником доменных решений. Они только обогащают контекст предложений.

## Affiliate

Affiliate-интеграции вписываются в модель:

`AffiliatePartner ↔ ExternalOffer ↔ TripExternalSelection`

Их роль:

- монетизировать внешний переход;
- привязывать offer к безопасной партнёрской ссылке;
- позволять backend контролировать outbound redirect и attribution.

Affiliate-слой не должен менять предложение для пользователя без явного отображения источника и условий.

## Другие внешние сервисы в рамках текущей архитектуры

Архитектура допускает и другие provider-категории, если они проходят через тот же backend-контур:

- travel content provider-ы;
- currency/price normalization сервисы;
- place enrichment;
- moderation или fraud-сигналы как вспомогательные backend-сервисы.

Добавление нового provider-а не должно менять доменную модель: оно должно встраиваться через `ExternalProvider`, `ExternalAPIRequest` и `ExternalOffer`.

## Общие правила интеграций

- Все секреты хранятся только на backend.
- Frontend не вызывает provider-ов напрямую.
- AI использует внешние данные только через backend orchestration.
- Внешние ответы считаются недоверенными, нормализуются и валидируются.
- Для пользователя сохраняются источник, время проверки и условия offer-а.
- Travel Friend не бронирует и не оплачивает внешние услуги за пользователя.
